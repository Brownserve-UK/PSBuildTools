# 2026-09-30 - GitHub Actions

First stab at Phase 1 of [2026-09-29 - Refactor](../prompts/2026-09-29%20-%20Refactor.md).
The goal is to understand the overall shape well enough to start drawing up contracts. Nothing here is decided.

## Where we are today

### Inventory

14 workflow templates across 5 project types, generated by `Compare-BrownserveRepository` and written by `Initialize-` / `Update-BrownserveRepository`.

| Workflow | Templates | What actually differs between them |
| --- | --- | --- |
| `label-pr` | 1 (`psmodule_`, used by every type) | Nothing. Byte-identical in all 4 live repos. |
| `stage-release` | 3 (`psmodule`, `rustapp`, `webapp`) | A step name, a comment, whitespace, and an extra `rustup` step for Rust. Effectively one workflow. |
| `builds` | 5 | The "relevant files" regex. Rust types add an OS matrix plus a gate job; `bsdev` adds a container smoke-test job. |
| `release` | 5 | Publish targets and their secrets, `mono` for NuGet, a Rust packaging matrix, docs deploy (MkDocs vs Astro). |

Every template does the same core thing: checkout into `path: <repo name>`, then call `.build/build.ps1 -Build <target>`. The checkout path exists because `_init.ps1` derives `$Global:BrownserveRepoName` from the folder name, and it is the only reason we need `###REPO_NAME###` templating at all.

### Drift in the live repos

Comparing the PSTools repos and `bsdev` against their templates:

- Almost all drift is Dependabot pin bumps (`checkout` v6 to v7.0.1, `setup-python`, `upload-artifact`, `download-artifact`). Running `Update-BrownserveRepository` today would roll all of these back. This confirms problem 1 in the brief.
- `bsdev/release.yaml` has one intentional hand edit (a `publish_to` input) that an update would also wipe.
- Version comments are unreliable: several SHAs that Dependabot moved to v7 still say `# v6`, because major-only comments are not rewritten.

### Other things worth knowing

- Terraform requires the check names `BuildTestAndCheck` and `label-pr` on every public repo with CI. Any change to job naming is a coordinated Terraform change.
- `release` and `bsdev` interpolate `workflow_dispatch` inputs straight into `pwsh` (`PublishTo = ${{ inputs.publish_to }}`). That is the classic script-injection pattern and should not survive the move.
- The Slack step re-runs `_init.ps1` (full paket restore) purely to call `Send-BuildNotification`.
- Private repos on the free tier get no branch protection and no org secrets (Terraform copies secrets per repo). Anything we build must not assume org-level secrets.
- `Brownserve-UK/actions` already exists in Terraform ("GitHub Actions workflows for Brownserve projects"). The local clone has no files. We need to decide whether to reuse the name.
- The `.github` org repo exists and is public. It can host org workflow templates (`workflow-templates/`), which may help with bootstrapping new repos.

## Terminology

The brief is unsure about "composite (re-usable?)". These are different things in GitHub Actions and the difference drives the whole design.

| Term | What it is | Unit | Lives in |
| --- | --- | --- | --- |
| Composite action | An `action.yml` with `runs.using: composite` | A **step** | Any directory with an `action.yml` |
| JavaScript / Docker action | Same, with code | A **step** | Any directory with an `action.yml` |
| Reusable workflow | A workflow with `on: workflow_call` | One or more **jobs** (own runners, matrix, permissions) | Must be in `.github/workflows/` |
| Caller workflow (stub) | A normal workflow whose job does `uses: <reusable workflow>` | Triggers only | The project repo |

The brief's `new-pr` example (label the PR, then notify Slack) is job-level orchestration, so it is a **reusable workflow**, not a composite action.

## Proposed shape

Three tiers. Each tier only depends on the tier below, pinned by SHA and bumped by Dependabot.

```text
Tier 1: leaf actions            one repo per action, versioned per action
        Brownserve-UK/action-label-pr, action-notify, ...
              ^ pinned SHA, Dependabot bumps
Tier 2: shared workflows        one repo, versioned as a whole
        Brownserve-UK/workflows  (.github/workflows/ci.yaml, release.yaml, ...)
              ^ pinned SHA, Dependabot bumps
Tier 3: caller stubs            a few lines in every project repo
        <project>/.github/workflows/*.yaml
```

### Tier 1: leaf actions

- One action per repo, own semver tags, own changelog. Matches the brief's hard rule.
- Default to composite actions (bash / `pwsh` / `actions/github-script` with a script file). JavaScript actions need a committed `dist/` and an extra npm update loop, so only when justified.
- Before writing one, check whether a well-maintained third-party action already does it (see [D4](#decisions-needed)).

### Tier 2: shared workflows

- **Reusable workflows only, no composite actions.** This answers the brief's "gotchas about this repo consuming its own actions":
  - Inside a reusable workflow, `uses: ./some-action` resolves against the **caller's** checkout, not the workflow repo.
  - So a Tier 2 workflow can only use a Tier 2 composite action by full `Brownserve-UK/workflows/path@ref`, and that ref has to be bumped on every release. That is exactly the "release needs to update itself" pitfall.
  - Keeping step-level logic in Tier 1 sidesteps it completely. Tier 2 becomes pure orchestration.
- Whole-repo semver tags. Releasing is just tagging; no workflow file ever needs rewriting at release time.
- Workflows own **orchestration** (triggers mapping, runners, matrix, permissions, secrets, artifacts, gating, notifications). `build.ps1` owns **logic**. That line is the Phase 1 / Phase 2 contract.

### Tier 3: caller stubs

Some things can only live in the caller, so every project still needs a stub:

- Triggers (`on:`), trigger filters, and `workflow_dispatch` input definitions.
- The permissions **ceiling**. A reusable workflow can only reduce `GITHUB_TOKEN` permissions, never raise them.
- How secrets are passed (`secrets: inherit` or explicit).
- The pinned ref.

Illustrative only:

```yaml
---
name: ci
on:
  pull_request:
    branches: [main]

permissions: {}

jobs:
  ci:
    uses: Brownserve-UK/workflows/.github/workflows/ci.yaml@<sha> # v1.0.0
    permissions:
      contents: read
      pull-requests: read
    with:
      capabilities: '["powershell-module"]'
    secrets: inherit
```

Design goal: stubs should almost never change except for the pin, which Dependabot owns. Anything else changing in a stub (a new trigger, a wider permission) is a distributed-file change and lands on the "how do we update things" research question.

### Pipeline shape: lifecycle workflows with capability inputs

Two ways to cut Tier 2:

1. **Per capability** (`rust-build.yaml`, `container-smoke.yaml`, ...) composed in the stub. Stubs get fatter, and the gate job has to live in the stub because only it knows every job.
2. **Per lifecycle event** (`ci`, `pr-checks`, `stage-release`, `release`) with capability inputs that switch jobs on and off. Stubs stay tiny and the gate job stays central.

Leaning towards 2. It also lines up with dropping explicit project types: capabilities like `powershell-module`, `rust-app`, `container`, `docs-mkdocs`, `docs-astro` become the shared vocabulary instead of `bsdev` / `WebApp` etc.

## Versioning and propagation

- Tier 1 and Tier 2 both publish semver tags; consumers pin full SHA with a full-version comment (`# v1.4.2`, not `# v1`) so Dependabot keeps the comment honest.
- A Tier 1 fix reaches a project in two hops: Tier 2 bump PR, Tier 2 release, project bump PR. With `cooldown` (bsdev uses 30 days) that could take two months, so Brownserve-owned refs need excluding from cooldown and grouping into one PR.
- Release automation on Tier 2 (for example auto-release when a Tier 1 bump merges) is optional but would make the two-hop latency tolerable.

## Testing

- **Tier 1:** each repo tests its own action via `uses: ./` on PR, against fixtures. Its own CI and release must never depend on the version being released.
- **Tier 2:** a Tier 2 PR can call its own workflows via `uses: ./.github/workflows/x.yaml` (same commit) against fixture projects kept in the repo, e.g. a tiny PowerShell module and a tiny Rust crate.
- **Static checks everywhere:** `actionlint` and `zizmor` (free, security-focused, would catch the injection issue above). Comes towards the end of the process NOT at the same time as making the initial changes.
- **Canary:** optionally one low-risk project tracks Tier 2 `main` so breakage shows up before a release.

There is a loose circularity to watch: Tier 1 repos will want to use Tier 2 workflows for their own CI, while Tier 2 depends on Tier 1. It works because everything is pinned, but a broken Tier 1 release must not stop us fixing Tier 1.

## Contracts to draw up next

These are the boundaries this phase touches. Each needs a written contract before code.

| # | Contract | Covers |
| --- | --- | --- |
| C1 | Tier 1 action interface | Inputs, outputs, runtime choice, repo scaffold, release process, what counts as breaking |
| C2 | Tier 2 workflow interface | `workflow_call` inputs, secrets, outputs, required caller permissions, **emitted check names**, what counts as breaking |
| C3 | Tier 3 stub | What a stub may contain, who creates it, who may change it |
| C4 | Phase 2 boundary | `build.ps1` params, target names, secret env var names, artifact dir (`.tmp/output`), the checkout-path / repo-name assumption |
| C5 | Terraform boundary | New repos (and a Terraform preset for Tier 1 repos), required check names, secret distribution, GitHub App installation list |
| C6 | Update mechanism | Stubs and `dependabot.yml` are distributed files; whatever answers "how do we update things" owns them |
| C7 | Capabilities vocabulary | Shared by Tier 2 inputs, Phase 2 tasks, and whatever replaces project types |

## Rollout sketch

1. Create Tier 1 `action-label-pr` and a Tier 2 `pr-checks` workflow. Lowest risk, already identical everywhere.
2. Move one repo to a `pr-checks` stub. Update its Terraform required check in the same change, because the check name becomes `<caller job> / <called job>`.
3. Repeat with `ci`, then `stage-release`, then `release`, one repo at a time.
4. `Update-BrownserveRepository` stops owning full workflow files for migrated repos (at most it creates stubs once).

## Decisions needed

- **D1.** Tier 2 holds reusable workflows only, no composite actions? (Recommended, see above.)
- **D2.** Pinning for Brownserve-owned refs: SHA plus Dependabot (deterministic, recommended) or floating major tags like `@v1` (instant rollout, non-deterministic, flagged by `zizmor`).
- **D3.** Lifecycle workflows with capability inputs, or per-capability workflows composed in stubs? (Leaning lifecycle.)
- **D4.** Use established third-party actions where they fit (`dorny/paths-filter`, `re-actors/alls-green`, `slackapi/slack-github-action`), or own everything?
- **D5.** Repo names: `action-<name>` for Tier 1 and `workflows` for Tier 2? What happens to the existing `Brownserve-UK/actions` repo?
- **D6.** Auto-merge Brownserve-owned Dependabot bumps, and auto-release Tier 2 when they land?
- **D7.** Does `label-pr` stay its own `pull_request_target` workflow, or fold into `pr-checks` alongside other PR hygiene?

## Things to verify

Believed true but not yet confirmed against current GitHub docs or a spike.

- **V1.** Dependabot bumps `uses: owner/repo/.github/workflows/x.yaml@<sha> # vX.Y.Z` in callers, including the comment.
- **V2.** Inside a reusable workflow, `uses: ./action` resolves to the caller's workspace (underpins D1).
- **V3.** Inside a reusable workflow, `uses: ./.github/workflows/y.yaml` resolves to the same repo and commit as the calling reusable workflow. If so, Tier 2 workflows can compose each other safely.
- **V4.** Current limits on reusable workflow nesting depth and count per run.
- **V5.** Whether a reusable workflow can reliably discover its own repo and ref (needed if Tier 2 ever wants to check out its own scripts).
- **V6.** Required check naming through a reusable workflow, including matrix jobs, and how it maps to Terraform `contexts`.
- **V7.** Dependabot `cooldown` exclusions and `groups` patterns behave as expected for `Brownserve-UK/*`.
- **V8.** Immutable releases are available to us on the free tier for public repos.
