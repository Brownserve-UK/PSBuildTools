# 2026-09-30 - Paket

Research for the "Do we keep `paket`?" question in [2026-09-29 - Refactor](../prompts/2026-09-29%20-%20Refactor.md).
Nothing here is decided. [GitHub Actions](./2026-09-30%20-%20GitHub%20Actions.md) and [Invoke-Build Tasks](./2026-09-30%20-%20Invoke-Build%20Tasks.md) both depend on the answer, so it is worth settling before their contracts.

## Where we are today

### How paket is wired in

| Piece | What it does |
| --- | --- |
| `.config/dotnet-tools.json` | Pins the paket tool (10.3.1). Dependabot's `nuget` ecosystem already bumps this in the PSTools repos, but not in `bsdev`. |
| `paket.dependencies` | Generated by `New-PaketDependenciesFile`. One source (nuget.org) and bare `nuget <Id>` lines. Only the "Manually defined" section survives `Update-BrownserveRepository`. |
| `paket.lock` | Gitignored, **and** deleted by `_init.ps1` on every run (`$EphemeralFiles`). |
| `packages/` | Restore target, laid out as `packages/<Id>/` with no version folder. `_init.ps1` and the tasks hardcode paths like `packages/Invoke-Build/tools/InvokeBuild.psd1`. |
| `paket-files/` | Created and wiped by `_init.ps1`. Nothing uses it. |
| `nuget.config` | Generated in every repo, not used for restore today. The `psmodule` tasks build a temporary one for custom feed publishing. |

What gets restored: `Brownserve.PSCommon`, `Brownserve.PSSourceControl`, `Brownserve.PSBuildTools`, `Invoke-Build`, `Pester`, plus `NuGet.CommandLine` for PowerShell modules. All of them are tools-only packages (`tools/`, no `lib/`).

Outside paket entirely: `platyPS` and `powershell-yaml` come from PSGallery via `Save-Module`, unpinned. That is a second dependency channel nothing can see or update.

### What that means in practice

- Every `_init.ps1` run resolves the latest version of everything. The local lock files show it: `bsdev` resolved PSCommon 0.2 and Pester 6.0.1, PSBuildTools resolved PSCommon 0.2.1 and Pester 6.2.0.
- PSCommon and PSSourceControl pin exact versions (`= 0.2.1` etc.) inside the **auto-generated** section. The next `Update-BrownserveRepository` would silently drop them.
- We use none of paket's distinguishing features (lock-first workflow, groups, GitHub/HTTP file dependencies, framework restrictions). It is a plain NuGet downloader that lays packages out without version folders.
- Dependabot has no paket support. [dependabot-core#2190](https://github.com/dependabot/dependabot-core/issues/2190) has been open since 2019, and in July 2024 the NuGet updater's owner said they don't have the bandwidth for it. A September 2025 comment there reports Dependabot now fails on .NET projects that import paket rather than ignoring them. We have no project files so that doesn't bite us, but it shows the direction of travel.
- GitHub's dependency graph doesn't read paket files either, so we get no security alerts for these packages.

## What we need from a replacement

Pulled from the brief and the Phase 1 / Phase 2 research.

| # | Requirement | Source |
| --- | --- | --- |
| R1 | Updatable by Dependabot, including groups and cooldown exclusions for `Brownserve.*` | Brief |
| R2 | Deterministic: the exact version set is committed, so a rebuild gets the same tools | Brief |
| R3 | Resolves transitive dependencies, because the Phase 2 task package declares nuspec ranges on the modules | Phase 2 P7 |
| R4 | Free, no self-hosted infrastructure | Brief |
| R5 | Works with `pwsh` on Linux, macOS and Windows, locally and in CI | Today |
| R6 | Still provides `NuGet.exe` (mono stays) | Brief |
| R7 | Nice to have: one channel for PSGallery modules too | Today |
| R8 | Nice to have: visible to the dependency graph and security alerts | Today |

## Options

### A. Keep paket as it is

Floating latest, no lock. Fails R1 and R2. Baseline only.

### B. Keep paket, commit the lock, update it with our own workflow

- Stop ignoring and deleting `paket.lock`. `_init.ps1` runs `paket restore` (lock only) instead of `paket install`.
- A scheduled workflow (a Phase 1 Tier 1 action or Tier 2 workflow) runs `dotnet paket update` and opens a PR, e.g. with `peter-evans/create-pull-request`.

Good:

- Smallest change. `packages/<Id>/` layout and every hardcoded path stay as they are.

Bad:

- We end up owning a mini Dependabot: grouping, ignore rules, cooldown, release notes in the PR body, rebasing, conflicts.
- PRs raised with `GITHUB_TOKEN` don't trigger workflows, so it needs the GitHub App token. Signed commits (branch protection) need `sign-commits: true`, which commits through the API.
- Still no dependency graph or alerts (R8).
- It is a workflow, so allowed by the brief, but it is the closest thing to a custom bot on this list.

Verdict: viable fallback.

### C. An MSBuild project with `PackageReference` and a lock file

A small SDK-style project per repo, used purely as a dependency manifest. Illustrative only:

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>netstandard2.0</TargetFramework>
    <RestorePackagesWithLockFile>true</RestorePackagesWithLockFile>
    <RestorePackagesPath>$(MSBuildThisFileDirectory)../packages</RestorePackagesPath>
    <IsPackable>false</IsPackable>
  </PropertyGroup>
  <ItemGroup>
    <PackageReference Include="Brownserve.PSCommon" Version="0.2.1" />
    <PackageReference Include="Brownserve.PSSourceControl" Version="0.4.0" />
    <PackageReference Include="Brownserve.PSBuildTools" Version="0.3.0" />
    <PackageReference Include="Invoke-Build" Version="5.14.23" />
    <PackageReference Include="Pester" Version="6.2.0" />
    <PackageReference Include="NuGet.CommandLine" Version="7.9.0" />
  </ItemGroup>
</Project>
```

`_init.ps1` runs `dotnet restore <project> --locked-mode` in place of `dotnet tool restore` and `dotnet paket install`.

Good:

- **Dependabot native.** Its NuGet updater handles SDK projects, `packages.lock.json`, `dotnet-tools.json` and `global.json`. It bumps the reference and the lock file in one PR, with groups, cooldown, ignores and release notes. Dependabot commits are signed by GitHub.
- **Deterministic.** NuGet picks the lowest version that satisfies each range, so direct references are exact in practice. The lock file pins transitive versions and content hashes, and `--locked-mode` fails the build if the manifest and lock disagree.
- Transitive dependencies work (R3).
- The dependency graph reads `.csproj` files, so we get alerts (R8).
- No new tooling. The .NET SDK is already required, since paket itself is a dotnet tool. Paket and `paket-files/` go away.
- The lock file is a natural cache key for CI.
- PSGallery is a NuGet v2 feed, and Dependabot's NuGet updater supports v2 and v3 feeds. We could add it as a second source in `nuget.config` and restore `platyPS` and `powershell-yaml` through the same manifest (R7), using package source mapping so `Brownserve.*` only ever comes from nuget.org.

Bad, or at least different:

- **Layout changes** to `packages/<id-lowercase>/<version>/`. Every hardcoded path in `_init.ps1` and the tasks changes. Rather than guessing paths we should read them from `obj/project.assets.json` (or similar), which belongs in Phase 2's P5 environment contract.
- **Resolution semantics differ from paket.** NuGet picks the lowest applicable version for transitive dependencies, while paket picks the highest. If the Phase 2 task package says `Brownserve.PSBuildTools >= 1.2.0`, a project gets 1.2.0 unless it also references PSBuildTools directly. The simple rule: projects reference every module directly, and nuspec ranges act as compatibility guards. That is arguably what we want anyway.
- A `.csproj` in a PowerShell or Rust repo is a bit odd, and editors may offer C# tooling. Name and placement matter.
- NuGet checks framework compatibility. Tools-only packages should be fine, but a package with only `lib/net4x` would raise `NU1701`, and Dependabot refuses to update projects that suppress `NU1701`.
- Floating versions (`1.*`) exist, but Dependabot doesn't manage them and they undo R2. We shouldn't use them.

Sub-choices within C:

| # | Choice | Notes |
| --- | --- | --- |
| C1 | Inline versions or Central Package Management (`Directory.Packages.props`) | With one project, inline is simpler. CPM only earns its place with several manifests or real .NET projects in the repo. `Directory.Packages.props` applies to every project below it, so it would live in `.build/`. |
| C2 | Repo-local `packages/` or the global cache (`~/.nuget/packages`) | Repo-local keeps today's mental model and gets wiped each run. The global cache is shared across repos and faster, but `_init.ps1` must never wipe it. |
| C3 | Project name and location | e.g. `.build/dependencies.csproj` with Dependabot `directory: /.build`. Avoid `.proj`: Dependabot treats those as entry points that reference other projects. |
| C4 | SDK | Stick to plain `Microsoft.NET.Sdk`. There are reported Dependabot failures with packages referenced through MSBuild SDKs ([dependabot-core#11479](https://github.com/dependabot/dependabot-core/issues/11479)), so `Microsoft.Build.NoTargets` needs testing before we lean on it. |

Verdict: **leaning this way.**

### D. `packages.config` and `NuGet.exe install`

Tempting because we keep `NuGet.exe` anyway, and `nuget install packages.config -ExcludeVersion -OutputDirectory packages` reproduces today's layout almost exactly. But:

- Dependabot only finds a `packages.config` through a project that includes it, so we'd need C's project file anyway.
- `NuGet.exe` has to be downloaded, unpinned, before it can install anything (including itself).
- Mono becomes a requirement on every machine for every build, not just for publishing.
- It is a flat list: transitive dependencies are listed by hand and there are no content hashes.

Rejected.

### E. PowerShell-native managers

PSResourceGet required-resource files, PSDepend, ModuleFast. A natural fit for modules and PSGallery, but Dependabot understands none of them ([dependabot-core#13968](https://github.com/dependabot/dependabot-core/issues/13968), a PSDepend ecosystem request, has been open since January 2026). Fails R1 and R8. Only worth revisiting if Dependabot adds support.

### F. Further out

Noted for completeness. None of these replaces a manifest on its own.

- **Bake the tooling into a versioned CI / devcontainer image**, with Dependabot's `docker` ecosystem bumping the digest. That moves the problem into the image repo, which still needs one of the options above. It might pair with C later for speed.
- **Vendor packages into the repo.** Deterministic, but invisible to Dependabot and it bloats history.
- **Git submodules.** Dependabot tracks branch heads, not releases. Poor fit.

## How this touches the other research

- **Phase 1.** Dependabot `nuget` entries become part of the distributed `dependabot.yml` (C6). `Brownserve.*` updates should be grouped, excluded from cooldown, and possibly auto-merged (D6). Dependabot PRs only get Dependabot secrets, so `BuildTestAndCheck` must not need regular secrets.
- **Phase 2.** The task package becomes one more `PackageReference`, and propagation is a Dependabot PR per repo. The lowest-applicable rule feeds straight into P7. V7 there ("paket resolves transitive nuspec dependencies...") becomes the NuGet equivalent or goes away.
- **Latency.** Dependabot runs on a schedule, so a module release reaches consumers at the next run (daily at best).
- **The generator.** `Initialize-` / `Update-BrownserveRepository` must stop owning version lines, or we recreate the Dependabot versus generator fight from Phase 1. That leaves an open question about how capabilities add or remove packages (see D7).
- **Self-hosting.** PSTools repos still build using released versions of themselves, with Dependabot bumping them after each release. The Phase 2 working copy override is still needed.

## Migration sketch (if C)

1. Spike in one repo: the project, the lock, restore, path resolution in `_init.ps1`, and the Dependabot config. Work through the verify list.
2. Move the PSTools repos and `bsdev`. Remove `paket.dependencies`, the paket entry in `dotnet-tools.json`, `paket-files/` and the paket gitignores.
3. Optionally move `platyPS` and `powershell-yaml` into the manifest as a separate step.
4. Generator clean-up: `New-PaketDependenciesFile`, the `PaketDependency` classes and `paket_dependencies_config.json` go.

## Decisions needed

- **D1.** Replace paket with C, or keep it with a committed lock and our own update workflow (B)? (Leaning C.)
- **D2.** Lock everything, or only `Brownserve.*` and let third-party packages float? (Everything is recommended, since Dependabot makes locking cheap.)
- **D3.** Inline versions or CPM? (C1)
- **D4.** Repo-local `packages/` or the global cache? (C2)
- **D5.** Bring the PSGallery modules into the same manifest?
- **D6.** Auto-merge `Brownserve.*` Dependabot PRs? (Shared with Phase 1 D6.)
- **D7.** Who owns the manifest after creation? If the repo and Dependabot own it, how does a capability (e.g. `powershell-module` needing `NuGet.CommandLine`) get its packages added? This overlaps "how do we solve updating things".

## Things to verify

Believed true from reading the Dependabot NuGet updater source and docs, not yet confirmed with a spike.

- **V1.** `PackageReference` restores all our tools-only packages (including `developmentDependency` ones) under `netstandard2.0` with no warnings.
- **V2.** Dependabot updates a `.csproj` in `/.build` and its `packages.lock.json` together, with `groups` and cooldown exclusions for `Brownserve.*`.
- **V3.** The PSGallery v2 feed with package source mapping restores `platyPS` and `powershell-yaml`, and Dependabot updates them.
- **V4.** There is no way to trigger a Dependabot version update on demand after a release, so the schedule sets the latency.
- **V5.** `--locked-mode` works well locally as well as in CI, or we need a local-only flag to regenerate the lock.
- **V6.** Reading package paths from `obj/project.assets.json` is reliable cross-platform, including lowercase ids on Linux.
- **V7.** Dependabot commits satisfy the signed-commit branch protection.
- **V8.** The restore project's `obj/` and `bin/` output is gitignored and doesn't confuse other tooling (e.g. in Rust repos).

## Out of scope but noticed

- The exact-version pins in PSCommon and PSSourceControl sit in the auto-generated section of `paket.dependencies`, so they are one `Update-BrownserveRepository` away from being lost.
- The generated `.gitignore` comment contains a literal `` `n `` (an unexpanded PowerShell escape) and still refers to `Brownserve.PSTools`.
- `_init.ps1` creates `paket-files/` on every run even though nothing uses it.
